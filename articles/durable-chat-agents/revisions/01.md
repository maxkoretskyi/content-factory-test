# Why HTTP API Routes Are a Bad Fit for AI Agents (and Why Durable Runs Solve It)

When building early LLM integrations, a standard HTTP request/response route—like a Next.js API route, an Express handler, or a FastAPI endpoint—made perfect sense. A user sent a prompt, your backend forwarded it to OpenAI, and you streamed the text response back. The entire transaction took under three seconds.

But as soon as you transition from stateless chat completions to **AI agents**, the synchronous request/response model breaks down. 

An agent is not a single completion; it is a stateful, iterative loop. The LLM decides to call a tool, your backend executes the tool, feeds the result back to the LLM, and repeats until the task is complete. Attempting to run this multi-step loop inside a transient HTTP request introduces three structural architectural flaws.

---

## The Three Failure Modes of HTTP-Bound Agents

### 1. Connection Drops and Lost Work
When a user on a mobile device enters a tunnel, switches from Wi-Fi to cellular, or simply closes their browser tab, the TCP connection drops. In response, web servers and API gateways terminate the underlying request to save resources. 

If your agent is in the middle of a 30-second multi-tool loop, that execution is aborted mid-flight. Any tool calls currently executing in the background are orphaned, leading to inconsistent state, and your application loses the context of how far the agent had progressed.

### 2. Hard Timeout Limits
Modern web infrastructure is built for rapid, transient transactions. Vercel’s serverless functions have default timeouts ranging from 10 to 15 seconds (depending on your tier). AWS API Gateway enforces a hard 29-second integration timeout. 

An agent executing a sequence of slow tools—such as performing a web search, querying a vector database, and running a code sandbox—will easily breach these limits. You cannot configure your way out of these architectural constraints without moving to complex, self-managed infrastructure.

### 3. Wasted Tokens and Zero Checkpointing
If your agent loop fails on step 4 of a 5-step run due to a rate limit or a flaky third-party tool, standard API routes offer no way to recover gracefully. The connection is severed, and your only option is to restart the request from scratch. 

This means re-submitting thousands of tokens of context to the LLM for steps 1 through 3. At production scale, re-running redundant, expensive prompt windows due to downstream failures is incredibly expensive.

---

## The Solution: Decouple Execution with Durable Runs

To build robust agents, you must separate the **client connection** from the **agent execution**. 

Instead of processing the agent loop inside the HTTP handler, the API route should do only two things:
1. Validate the incoming request payload.
2. Trigger a **durable background run** and immediately return a `runId` with a `202 Accepted` status.

The client then reads agent progress asynchronously—either by polling an status endpoint, connecting to a WebSocket, or subscribing to a Server-Sent Events (SSE) stream.

A durable execution engine (such as Trigger.dev) allows you to write your agent loop as a series of checkpointed steps:

```typescript
import { task, step } from "@trigger.dev/sdk/v3";

export const researchAgent = task("research-agent", async (payload: { query: string }) => {
  // Step 1: Parse initial user intent (cached if repeated)
  const plan = await step("generate-plan", async () => {
    return await callLLM(`Create a search plan for: ${payload.query}`);
  });

  // Step 2: High-latency external tool execution
  const searchResults = await step("web-search", async () => {
    return await searchBing(plan.queries);
  });

  // Step 3: Analyze results using LLM
  const summary = await step("synthesize-findings", async () => {
    return await callLLM(`Summarize these results: ${searchResults}`);
  });

  return summary;
});
```

## Why Durability Wins

By shifting to a durable run model, your architecture changes fundamentally:

* **Step-Level Retries:** If the `web-search` tool throws a `503 Service Unavailable`, the engine retries *only* that step. The state of `generate-plan` is already saved to durable storage, so you don't waste tokens re-running step 1.
* **Network-Independent Execution:** If the user closes their browser, the background run continues to completion. When they reconnect, they can simply pull the completed state.
* **Infinite Execution Windows:** Because the run executes asynchronously, it can run for seconds, minutes, or even pause for days awaiting human-in-the-loop approvals.
