# Why HTTP API Routes Are a Bad Fit for AI Agents (and Why Durable Runs Solve It)

When building simple LLM integrations, a standard HTTP request/response route—like a Next.js API route or Express handler—makes sense. The client sends a prompt, your backend forwards it to OpenAI, and you stream the text response back in under three seconds.

But as soon as you transition from stateless chat completions to **AI agents**, the synchronous request/response model breaks down. 

An agent is a stateful, iterative loop, not a single completion. The LLM decides to call a tool, your backend executes it, feeds the result back, and repeats until the task is complete. Running this multi-step loop inside a transient HTTP request introduces three structural architectural flaws.

---

## The Three Failure Modes of HTTP-Bound Agents

### 1. Connection Drops and Lost Work
When a mobile user enters a tunnel, switches Wi-Fi networks, or closes a browser tab, the TCP connection drops. In response, web servers and API gateways terminate the underlying request to save resources. 

If your agent is mid-way through a 30-second multi-tool loop, execution is aborted. Any running background tools are orphaned, database states become inconsistent, and you lose the entire execution context.

### 2. Hard Timeout Limits
Modern web infrastructure is built for transient transactions. Vercel’s serverless functions have default timeouts of 10 to 15 seconds (depending on your tier). AWS API Gateway enforces a hard 29-second integration timeout. 

An agent executing a sequence of slow tools—performing a web search, querying a database, and running a sandboxed script—will easily breach these limits, causing abrupt terminations.

### 3. Wasted Tokens and Zero Checkpointing
If your agent loop fails on step 4 of a 5-step run due to a rate limit or a flaky third-party API, standard routes offer no recovery mechanism. Because the HTTP request is aborted, you must restart from scratch. 

This means re-submitting thousands of tokens of context to the LLM for steps 1 through 3, wasting money on redundant API calls.

---

## The Solution: Decouple Execution with Durable Runs

To build robust agents, you must separate the **client connection** from the **agent execution**. 

Instead of running the agent loop inside the HTTP handler, your API route should do only two things:
1. Validate the incoming payload.
2. Trigger a **durable background run** and immediately return a `runId` with a `202 Accepted` status.

The client then reads progress asynchronously by polling a status endpoint or subscribing to a Server-Sent Events (SSE) stream.

A durable execution engine (like Trigger.dev) allows you to write your agent loop as checkpointed steps:

```typescript
import { task, step } from "@trigger.dev/sdk/v3";

export const researchAgent = task("research-agent", async (payload: { query: string }) => {
  // Step 1: Parse initial user intent (cached)
  const plan = await step("generate-plan", async () => {
    return await callLLM(`Create a search plan for: ${payload.query}`);
  });

  // Step 2: High-latency external tool execution
  const searchResults = await step("web-search", async () => {
    return await searchBing(plan.queries);
  });

  // Step 3: Analyze results using LLM
  const summary = await step("synthesize-findings", async () => {
    return await callLLM(`Summarize: ${searchResults}`);
  });

  return summary;
});
```

## Why Durability Wins

By shifting to a durable run model, your architecture becomes highly resilient:

* **Step-Level Retries:** If step 2 fails, the engine retries *only* step 2. The state of step 1 is preserved in durable storage, meaning zero wasted LLM tokens on retry.
* **Network Independence:** If the user disconnects, the run continues to completion. When they reconnect, they simply fetch the completed state.
* **Infinite Latency Tolerance:** Runs can execute for minutes, hours, or even days if they require human-in-the-loop approvals.
